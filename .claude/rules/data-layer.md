# Data layer

## Data Layer (dual-track Firestore)

- **Server side**: `src/lib/db/firestore/*.ts` — repository classes (`FirestoreCardRepository`, `FirestoreUserRepository`, plus connection/notification) using the admin SDK, enforcing visibility (`public` / `connections` / `private`) in code. Connections use a sorted `uid1_uid2` pair id.
- **Client side**: `src/lib/db/firestore/client/*` — direct read/write modules (cards, feed reads, invites, notifications, profile) consumed by SWR hooks in `src/lib/data/hooks.ts`; security is enforced by `firebase/firestore.rules`.
  Writes that reach another person or must be unique — publishing, pen names, messages, notes, resonating with a card already written — go through `/api/v1` like the apps (`callApi` in `client/api.ts` sends the ID token as a Bearer token), and the rules refuse them from the browser.
  Saving an edit to a published card goes through it too: the editor autosaves into `cards/{id}/edits/current` and the server applies that (`POST …/edits/apply`; the rules still let the author write the card, for older app builds).
  What stays client-direct is the author's own drafts and settings, reads, and a few narrowly checked legacy paths.
  The repo and web config are public: a rule is the only guard on a client write, so every new one needs field-level checks (key whitelist, types, sizes — the same limits the server applies when it copies content, `cardContent.ts`) and a `test/emulator/rules.emulator.test.ts` case.
  A card read failing for any reason but permission-denied / not-found (`isAbsent()` in `client/errors.ts`) throws rather than reading as "no such card", so SWR retries.
- **Anonymity**: an anonymous card's document names its author, so the rules let only the author read or list it; every public client list must say `where('anonymous', '==', false)` (composite indexes exist for each).
  Everyone else gets an anonymous card from the server, which leaves the author out: signed in through `/api/v1`, signed out through `GET /api/cards/view` (the card page falls back to it) and `GET /api/cards/latest` (the home feed).
  Card links are server-only; a link into someone's anonymous card shows on their profile only to them.
  So are a story's kept translations (`cards/{id}/translations/{to}`, round 25: the rules refuse every read and write, the author's too — a reader gets one through `POST /api/v1/cards/{key}/translation`, which asks who may read the card) and the card's own `summaryTranslations` (the feed's translated title and excerpt: the rules take it from no client); `deleteCard` deletes the kept translations in its own transaction by their exact paths, the account purge with the card's tree.
  So are a card's tap passages (round 27: `cards/{id}.tapPassages = { of, items: [{ id, text }], model, at, failed? }`, `of` the story's `passagesHash` — its plain text, so a formatting-only edit keeps them; written by `makeTapPassages`, never `updatedAt`; the rules take it from no client) and a reader's pick, `passage: { id, text } | null` on their `resonanceTaps/{cardId}_{uid}` document (the words themselves, kept after an edit; `setTap` off sets it null, on again writes the document without it).
  Notes are readable by their recipient only; a note on a named card is also a message in the two people's conversation (below), one on an anonymous card never is — not even between two people already connected — and never opens, counts toward or answers a letter (Safety).
  A block never hides an anonymous card nor refuses what is aimed at one (Safety).
  An anonymous card is public or private, never for connections only (Safety).
  Publish always writes a boolean `anonymous`.
- **Browser SDK**: client modules use Firestore Lite through `src/lib/db/firestore/client/sdk.ts` (writes land in call order; reads wait for this browser's writes in flight) — import from `./sdk`, never `firebase/firestore` (sdk.test.ts fails otherwise).
  The only realtime surface is `client/realtime.ts` (full SDK), reached through `listenLazily` (`client/listen.ts`) — an open thread, and the header's badges (`lib/data/live.ts`: one listener per key, shared, lingering 60 s after its last reader: the newest 50 conversations, the newest 20 bells); the two SDKs' Timestamps are different classes, so map listener data by shape.
  The landing and policy pages load no Firestore for a signed-out visitor; modals and the thought map's editor load on first open (next/dynamic).
- **An open thread** (`useChatThread` in `lib/data/thread.ts`; its pure pieces in `src/lib/chat`, twins of the apps' kit/chat): the newest 50 messages live, older pages read through Lite before the oldest held (`getOlderMessages`: a cursor of the send time to the microsecond plus the id — never a Date, which would skip messages), a search reading the whole history (≤ 5000).
  The viewer's sends go through the conversation's outbox (`outboxOf`, kept for the page's life): drawn at once, sent in order under a `clientId` the server makes the document id (the row keeps it as its key), a passing failure stops the line, a refusal fails only its message.
  A picture (the composer's 「＋」 · 圖片, or pasted; `preparePicture` scales it on the device) goes up as its message is sent, under that same `clientId` (`uploadChatImage`), and is drawn from the device meanwhile and after (`lib/chat/localPictures`); others' are read with the session cookie (`PicturePart`, the thread's size; the viewer, as kept).
  A message may carry `reactions` (by uid, the five `Reaction` ids — one this build doesn't know drawn as nothing) and `unsentAt` (then nothing else); a quote `unsent: true`, the list's `lastMessage.unsent`.
  The viewer's own reaction or unsend is drawn at once (`withLocalChange` in `lib/chat/message`, kept by message id until the listener's copy says the same — an older page is never heard again), a failed reaction put back with the `reactError` toast; `MessageHistory` counts a change of reactions, `unsentAt` or picture as news (`sameMessage`), or a reaction would never reach an open thread.
- **Signed-in pages read through `/api/v1`**, one request each: the card page's surroundings (`useCardPageLists`: `GET /cards/{id}?include=resonances,related,links,embeds`), a profile (`useProfilePage`: `GET /users/{handle}?include=cards,links`), a thread's cards — shared ones and Resonance card links (`useCardSummaries`: `GET /cards?keys=`, 30 per request, each card asked for once; the answer names the cards it covers, `asked`, and the ones whose request failed, `failed`, which their embeds read themselves).
  Signed-out readers stay on Firestore through the rules, except the home feed and anonymous cards (above); `useReadPath()` picks ('v1' / 'public' / null while auth restores).
  API summaries become list Cards through `lib/data/summaries.ts` (marked `summary`, never used to prefill a card page); story embeds find their card in `CardEmbedSourceContext` when the page provides one.
  The card ⋯ (`CardActionsMenu`) changes visibility and deletes through `PATCH`/`DELETE /api/v1/cards/{id}`, which revalidate on the server.
- **SWR defaults** live in `SWRProvider` (`SWR_DEFAULTS`: no focus revalidation, 30 s dedupe); hooks opt back in with `LIVE_ON_FOCUS` (conversations, block list) or keep a short window with `OWN_CONTENT` (anything the viewer edits).
  Profiles go through one page-wide cache (`getUsersByIds` in `client/reads.ts`: a get per profile, 30 at a time — the rules list no profiles —, 5-min TTL; `forgetCachedUser(uid)` after writing a profile).
  Never batch-read cards with `in` — the rules refuse the whole query when one card is unreadable.
  List clicks seed the card page's cache (`cardKey()` / `usePrefillCard()` in `src/lib/data/cardPrefill.ts`).
  The card page's 用卡片回應 (round 26: 共振 is the tap now, below) opens `ResonatePicker` (write a new card, or pick a published public card of yours answering nothing: `resonateChoices`; a tap marks it, 回應 sends it), and the owner's ⋯ takes a reply back (取消回應); both then re-read what shows the link through `useResonanceRefresh()` (`src/lib/data/resonate.ts`): the original's button, both cards' pages, the published and resonated shelves, the thought map.
  A published reply turns the segment into ✓ 已回應, which opens it; a draft one says 修改.
  **The end row** (round 26): signed in, the card page's only SWR answer is `cardPageKey(id, uid)` (`useCardPageLists`, `CardDetail.tap` with the lists); `useTapToggle` (`src/lib/data/taps.ts`) writes the tap into it optimistically and puts back only the latest flip; `withMine` keeps the whole list of faces and leaves `more` alone — `TapFaces` takes the first three as it draws (`shownFaces`). A reader's list of who resonated is SWR key `['taps', cardId, viewerId]`; the author's keeps its key (only the author reads it).
  **Reading reports** (`src/lib/data/readingReport.ts`, round 26): a page view's running totals (never a difference) go to `POST /api/v1/cards/{id}/reading` when the page hides, is left (`pagehide`) or unmounts — a keepalive fetch with an ID token while that token has more than 60 s to live (`fetchCreds` keeps the expiry `getIdTokenResult()` gives and forces a refresh 5 minutes before it — at once when the first, the SDK's cached token, has less, a minute later when a forced one still comes back short — and, on the page showing again, only when it has no token or one within those 5 minutes), else `sendBeacon` with the `__session` cookie, else nothing; `pageshow` persisted starts a new session; nothing for the author's own card, a private card or a shared-card pass. The apps keep unsent reports (iOS UserDefaults, Android `reading-reports.xml`; apps.md).
  `notificationSettings`' `isOn` counts `messages` and `resonanceTaps` on unless `false` (`ON_UNLESS_OFF`), every other switch on only when turned on.
  The card box reads the shelf on screen only (`useMyCardBox(shelf)`, key `cardbox:{uid}:{shelf}`): the viewer's own shelves through the rules, others' cards (resonated, linked, bookmarks) and the trash from `GET /api/v1/me/cards?tab=`.
  A card is 公開, 匿名公開 or a 私人卡 — its author's alone, finished or not (the word 草稿 is gone): the 私人卡 shelf (key `draft`) holds never-published cards and published private cards together (`getMyDrafts`, the most recently changed first), every 私人卡 opens its card page — from the card box and the trash (the thought map opens every card of the viewer's in the writer, private or not) — where its author sees 🔒 私人卡 at the end of the meta line and a 編輯 pen before the ⋯ — whose first item is then 公開發表 (the writer's publish step with 公開 chosen: `?step=publish&audience=public`), never a second 編輯 —, and the ⋯'s visibility row is 轉為私人卡 on a card readers have only (a 私人卡 is shared from the writer's step).
  The data is unchanged: a published private card keeps its `publishedAt` and slug, a never-published one is published only when it is shared; a writer typed into and emptied again leaves no card.
  The trash shelf shows its cards with no line under them; restoring one says who reads it now (`restoredAs()`: 已還原為私人卡 / 公開卡片 / 匿名公開卡片 / 僅連結的人看得到 — the toast is the only word that a public card is public again).
  The trash's moves from the web (move, restore, delete for good, empty) go through `useTrashActions()` (`src/lib/data/trash.ts`), which reads again what showed the card — every shelf, the profile lists, the thought map, the card's page — and takes a card being trashed or deleted for good off the card box's shelves at once (a refusal puts it back, said in a toast; the apps' card boxes do the same, no skeleton); the card ⋯'s 刪除 moves it to the trash with the shell's undo toast (`useToast`), and the one dialog that can outlive the control that restored a card (a resonance back on its own) is `RestoredAloneNotice`, drawn once by each page that restores.
  `getMyBlockedIds` waits for Auth to restore the viewer and is read beside each list's cards.
  `useMediaQuery` is null until hydrated.

**Server-only collections of round 26** (the rules refuse every client read and write; each that holds a uid, in a field or its id, joins `collectAccountData()`, Safety — `config/recommendPool`, the pool's numbers rewritten whole by warm-picks, holds none and doesn't): `resonanceTaps/{cardId}_{uid}` (composite index `cardId, on, at desc`); `readerSignals/{uid}_{cardId}` (a TTL policy on `expireAt` — the last reading + 180 days —, `sessions` and `days` exempt from indexing, `expectedSeconds` kept so "read in part" can be `min(progress, active ÷ expected)`); `cardSignatures/{cardId}` (`authorId`, version 3, `model`, `embedModel`, `insights[]`, `throughLine`, `moodOnly`, `insightScore`, `lifeDomain`, `emotionalRegister`, `placeholder`, `listedForStrangers`, `templated`, `rewritten`, `error`, `usage`; `insights` and `usage` exempt) — the card itself keeps only `signature: { placeholder, coreInsight, contentHash }` and the server-only `indexPendingAt`; `cardVectors` ids `{cardId}__{channel}__{part}` (with `part`, `embedModel`, `span`; an upsert replaces the card's parts whole); `config/recommendPool` `{ mu, r, tau, tauSituation, cards, embedModel }` (`mu`, `r` exempt); `recommendations/{uid}.shown` `{ cardId: { n, lastDay } }` (exempt) and `coldStart`; `userProfiles/{uid}` `{ taste: [{ cardId, w }], against, updatedAt }` — card ids and weights only. `CardDetail.tap` reaches clients through `/api/v1` alone.

Core entities live in `src/lib/db/types.ts`: `Card` (with `translations`, `tags`, `slug`, counters), `User` (`handle`/`handleLower`), `Connection`, `Invite`, `Resonance`, `CardLink`, `Notification`. `src/lib/adapters/` converts Firestore data to UI models.

After editing `firebase/firestore.rules` or `firebase/firestore.indexes.json`, deploy from the `firebase/` directory (that's where `firebase.json` lives — the command fails at repo root): `cd firebase && firebase deploy --only firestore:rules,firestore:indexes`.
