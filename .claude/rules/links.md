# Link previews

**Link previews** (`src/lib/links`; the server fetches an address a stranger wrote, so everything here is deny-by-default): `url.ts` is the one rule for what counts as a link — `firstLink`/`findLinks`/`normalizeLink`: http(s) only, no userinfo or `@`, port none/80/443, a host with a dot and ASCII (IDNs only as punycode), ≤ 2048 characters, trailing sentence punctuation (CJK too) and unbalanced `)` trimmed — written to be mirrored word for word by the web `linkify`, the Android `Linkify` and the iOS one.
`unfurlMessage` (after the response, ≤ 8 s) takes the message's first link, fetches it with `safeFetch` and writes `preview: { url, title, description?, siteName?, image? }` onto the message, where the live listener delivers it (a client renders a message without it and again when it arrives); the result is remembered per instance (`memo.ts`), so a link sent over and over is fetched once.
`safeFetch` resolves the name itself and refuses the fetch if ANY address is not public (`ip.ts`: IPv4 special-purpose blocks, IPv6 outside global unicast and its carve-outs, mapped forms judged by the IPv4 inside), connects to the vetted address through a pinned `lookup` (DNS rebinding), follows at most 3 redirects by hand re-vetting each hop, sends no cookie, Referer or credential (so a link to our own `/api` carries no session), has one 5 s deadline, reads a page to `</head>`/512 KB (a gzip bomb only that far), a JSON answer to 64 KB and an image to 5 MB (either refused past it), and takes `text/html` pages, `application/json` (mode `json`) and non-SVG `image/*`.
A YouTube video (`oembed.ts`: youtube.com, www./m./music. and youtu.be, an 11-character id at /watch?v=, /shorts/, /live/, /embed/, /v/ or youtu.be/ — its page's head is over 512 KB of script before any title) is previewed from YouTube's oEmbed endpoint instead, in JSON mode, through a request built from the id alone: its title and channel (as the description) through `cleanText`, site name `YouTube`, the thumbnail only from i.ytimg.com (else `/vi/{id}/hqdefault.jpg`) through the signed proxy; a private or removed video (401/404) has no card.
`openGraph.ts` reads the head tolerantly (comments, scripts and unterminated tags cannot hide or multiply tags) and treats every string as data: entities decoded once, tags, control, zero-width and direction-override characters removed, title ≤ 160, description ≤ 300, site name ≤ 80.
The picture never goes to clients from the page's site: `imageProxy.ts` signs the `og:image` URL (HMAC-SHA256; key `LINK_PREVIEW_SECRET`, else HKDF of `FIREBASE_PRIVATE_KEY`, else a fixed key outside production only — changing it orphans stored previews' pictures, not their text), stores a site-relative `/api/link-image?u=&s=` path, and on request verifies the signature in constant time before anything else, sniffs the bytes (SVG, PDF and the rest are refused whatever the header said), decodes with sharp (≤ 30 MP, first frame, `failOn: 'error'`), and remembers every outcome by URL with at most 3 pictures decoding at once (503 beyond a short queue): a picture 10 min, a refusal the address would earn again (blocked, not a picture, too big, unreadable) 5 min, a failure that may pass (timeout, network, DNS, a non-2xx status: `mayPass`) 15 s, the second in a row 1 min and from the third 5 min like a refusal (a picture, or a failure long after the last was forgotten, starts the run again: this memory is all that stands before the decode slots, so a site that never answers must not hold them) — and its 404 is `no-store`, so no browser, CDN or app keeps a failure and the next view of the preview gets the picture.
A signature stops strangers choosing an address, not a reader asking again and again — hence the memory and the limits.
Both link-preview keys — the pictures' and the drawn cards' versions' — come from one resolver, `previewSecret.ts` `linkPreviewKeys()` → `{ source: 'env' | 'derived', link, share }` (任務 #3 Phase 0): `LINK_PREVIEW_SECRET` is either `derived-v1:<link>.<share>`, today's derived keys pinned as `scripts/ops/link-preview-secret.ts` prints them, or any other text as before; a production process whose keys are derived logs it once; the derived fallback stays until owed.md's item has the value in Vercel, and goes in a later change.

**Link-preview image** (`src/lib/linkImage`, `/api/og/card`): a public card without a cover is drawn at 1200 × 630 as the feed card (backdrop, paper, its id's outline, title, `sharePassages` opening, byline, wave + Resonance lockup) in the reading design's type, with next/og from static instances in `src/lib/linkImage/fonts` (OFL beside them; `scripts/linkImage/build-fonts.py`; Big5 level 1 + Latin, shipped by next.config's tracing) — its `?v=` is made from exactly what `drawnCard` draws, keyed (an HMAC, from `LINK_PREVIEW_SECRET` or `FIREBASE_PRIVATE_KEY` — `shareVersionKey`) so the version of a drawing under a pen name can't be made from public data, an anonymous card's model never holds its author (匿名 over the "·" avatar), and what no font draws is left out first (`drawable`: a letter as □, a space as a plain one, a line or paragraph separator as a line feed, the rest dropped), since next/og would fetch any missing glyph but a tab's or a line feed's — a space's too — from Google Fonts mid-render.
The apps' 9:16 share image takes the same recipe from `src/lib/share/shareCard.ts` (`native/fixtures/share-card.json`, `UPDATE_SHARE_CARD=1`; its opening: `share-passages.json`, `UPDATE_SHARE_PASSAGES=1`); an anonymous card's canonical and og:url are its id, and pages name `fb:app_id` when `NEXT_PUBLIC_META_APP_ID` is set.

**Story link previews** (`storyLinks.ts`, `cardLinks.ts`): a paragraph whose only content is one http(s) link whose words are its own address — `<url>`, `[url](url)`, `[www.x.com](http://www.x.com)` (`wordsAreTheAddress` in `links/soleLink.ts`: the words, trimmed, an address `normalizeLink` takes naming the same page once `http(s)://` and one trailing `/` are set aside), a reference link so worded (no picture inside), or plain text that is exactly one `findLinks` match — is a *standalone link*; a link the writer gave words of its own reads as those words, alone on its line or not (round 16: the choice 卡片 / 文字 lives in the Markdown itself); every other link stays inline.
`standaloneLinks(story)` reads the story as CommonMark without GFM, as the apps' parsers do (a bare URL is text there), and leaves out our own hosts (`SITE_HOSTS` + `siteUrl()`'s) and IP addresses, each link once, at most 10; `native/fixtures/story-link-cards.json` pins the rule for the web and both apps (`soleLinks` = what a parser finds, `links` = what the server stores).
After publish and apply (never for a draft) `unfurlCardLinks` writes the server-only `linkPreviews` (reading order) and `linkPreviewsFor` (the links they were made for) onto the card: stored entries are reused for links still there, only new links are fetched (3 at a time, one 15 s deadline, through the memory `rememberedPreview` shares with chat; the author's `unfurl` bucket pays per new link, and over it the previews are skipped, never the save), the write re-reads the story in a transaction, removes both fields when no standalone link is left, writes nothing when nothing changed, and never touches `updatedAt`/`excerptAt`.
Readers take previews only through `linkPreviewOf`/`linkPreviewsOf` (`previewShape.ts`, client-safe: http(s) and a title required, a picture only from `/api/link-image?`) — chat messages, client `mapCard`, the card page's seed (`PublicCard.linkPreviews`, so `/api/cards/view` too) and v1 `CardDetail.linkPreviews` (anonymous cards too: they name pages, not people).
The web reader doesn't re-derive the rule under GFM: `StoryMarkdown` asks `soleLinkParagraphs(source)` which paragraphs (by source offset) are standalone and under which URL, and draws `StoryLinkCard` for one whose URL has a preview (`StoryLinkPreviewsContext`, provided by the card page), and for one without (a private or never-published card, an older build's story) the writer's quiet fallback card — host over address, no picture, no fetch — so 卡片 always looks like a card; our own hosts and IP addresses stay plain links.
The writer draws the same block: a `linkCard` atom node in `editorSchema.ts` (serialized `<url>`, parsed from a lone address-worded link or bare address; `/card/` stays `CardEmbed`), made by the link editor (`storyLinkEdit.ts`: the web bubble's 「連結」, ⌘K, the ＋'s 插入連結, the apps' format-bar link sheet — field, 顯示為 卡片 | 文字 only for a standalone link, 移除連結, 完成; 文字's words are the host without `www.` + path, which no rule reads as an address), and in the island by `exec('link', { href, display })` / `exec('unlink')`, `state.link` + `canCard`, `linkTap`, `setLinkPreviews`.
A story changed outside publish/apply (older app builds) keeps stale previews harmlessly — a client draws a card only for a link still standing alone — until the next save or `backfill.ts link-previews`.
